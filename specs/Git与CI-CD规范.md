## 1. 目的

统一 git 提交行为与自动化验证交付：保证提交历史**可读、可追溯、可回滚**，并把总纲质量门从 "人工检查" 升级为**机器门禁**。

## 2. Git 提交规范

### 2.1 提交信息格式

采用 Conventional Commits 风格：`<type>(<scope>): <subject>`

| type    | 含义            |
| ------ | -------------- |
| feat   | 新功能           |
| fix    | 缺陷修复          |
| docs   | 文档变更          |
| test   | 测试变更          |
| refactor | 重构（不改变行为）     |
| perf   | 性能优化          |
| build  | 构建 / 依赖变更     |
| ci     | CI/CD 配置变更    |
| chore  | 其他杂项          |

示例：`feat(订单模块): 新增批量导出功能`

* subject 用中文，简短陈述 "做了什么"，必要时在正文说明 "为什么"；

* 一个提交对应一个逻辑变更，禁止把无关改动混入同一提交。

### 2.2 提交粒度与内容



1. **小步提交**：按逻辑单元拆分提交，便于回滚与评审。

2. **同步提交**：代码变更必须与其对应的文档、测试用例在同一提交（或同一批提交）中同步更新，保持三者一致。

3. **禁止提交**：

   * 机密信息（密钥、token、cookie、open_id 等）；

   * 构建产物、临时文件、本地环境文件（以 `.gitignore` 排除）；

   * 大文件（优先使用 Git LFS 或外部存储）。

### 2.3 分支与合并



1. 主分支受保护：不直接向主分支推送（除非项目为单人维护且用户明确允许）；变更走分支 + 合并请求。

2. 合并前必须通过质量门（总纲第 5 节）与 CI 门禁（见第 3 节）；需要评审时按 VCS-REV-001 完成评审后再合并。

### 2.4 提交前自检



* [ ] 已运行测试 / 构建，验证通过；

* [ ] `git diff` 检查：无越界改动、无无关文件；

* [ ] 提交信息符合本规范格式；

* [ ] 无机密与临时文件进入提交。

## 3. CI/CD 规范

### 3.1 流水线阶段（推荐顺序）



```
静态检查/Lint → 单元测试 → 构建 → 接口测试 → 整体功能测试 → 文档与一致性检查 → 产物发布
```



1. **静态检查 / Lint**：格式、命名、潜在问题；

2. **单元测试**：核心逻辑全覆盖；

3. **构建**：产物可编译 / 可打包；

4. **接口测试**：对外接口行为验证；

5. **整体功能测试**：端到端关键路径；

6. **文档与一致性检查**（可选）：文档、测试与代码同步状态；

7. **产物发布**：仅由受控分支 / 标签触发。

### 3.2 质量门接入



1. 任一阶段失败即**阻断**流水线，输出失败证据（日志、报告），不静默跳过；

2. 全绿 = 满足总纲质量门的机器依据；发布动作只允许在全绿后执行；

3. 流水线配置变更按本规范 Git 部分的 `ci` 类型提交，与代码变更同步提交。

### 3.3 环境与依赖



1. Python 项目在 CI 中使用**独立虚拟环境**，依赖以锁文件锁定版本（对齐总纲「技术栈与环境约束」）；

2. 构建与测试环境保持与目标环境一致（版本、平台、依赖），避免 "本地能过、CI 挂"。

### 3.4 安全



1. 机密（密钥、token 等）通过 CI 平台的 Secret 机制注入，**不得**写入仓库或流水线文件明文；

2. 不得在 CI 中执行绕过检查的操作（如跳过测试、禁用 lint、`--no-verify`）。

### 3.5 触发策略



* 推送 / 合并请求触发检查类阶段；

* 发布类阶段仅由受控分支 / 标签触发，且需通过评审（按 VCS-REV-001）。

## 4. Git 与 CI/CD 协同规则



1. **CI 全绿是合并与发布的前置门禁**：合并请求在 CI 通过前不得合入（对接总纲质量门）；

2. 流水线配置变更走 git 提交规范（`ci` 类型），与代码变更同步提交；

3. CI 产物与报告按交付要求留存，作为评审员（VCS-REV-001）核实的证据。

## 5. 红线（MUST NOT）



1. 不得对共享分支执行 `--force` 推送，不得改写已推送的历史。

2. 不得用 git 存储或提交任何机密信息，不得将机密硬编码进仓库或流水线配置。

3. 不得在提交信息中编造变更内容，不得篡改或伪造 CI 结果。

4. 不得跳过验证直接提交 "看起来能跑" 的代码；不得在流水线中跳过测试 / 静态检查 / 构建验证。

5. 不得把 CI 当作生产执行环境运行业务任务。
