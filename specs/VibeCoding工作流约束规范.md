## 1. 目的

为所有基于 AI 辅助（VibeCoding）的开发任务提供统一的工作流与约束基线，确保每个任务满足：

* **可复现**：相同输入与流程应得到一致结果；

* **可验证**：一切改动都有验证动作，无验证等于未完成；

* **可审计**：变更、数据来源、决策依据可追溯；

* **不越界**：只改动被点名的范围，不破坏未要求的内容。

## 2. 核心原则



1. **验收先行是铁律**：任务开始前必须有明确目标与可检查的验收标准；目标模糊时不得开工，先澄清。

2. **先探查、后动手**：任何修改前先读取现有代码、结构与约定，不凭印象或二手摘要定位。

3. **最小改动、明确边界**：只改被点名的范围，保留未要求改动的内容及其原始状态、结论与备注。

4. **验证驱动**：每次改动都运行最小可行的验证（测试、构建、真实渲染、抽样重算），再宣告完成。

5. **安全与可逆优先**：不引入安全漏洞；破坏性、不可逆、影响共享系统的操作先说明风险并获得确认。

6. **事实有源**：每个数字、结论必须来自输入、具体信源或可复现计算；否则标注为待补充或估算并写明口径。

## 3. 工作流五阶段



```
需求 → 规划 → 编码 → 验证 → 交付
```



| 阶段   | 必做（MUST）                        | 禁做（MUST NOT）                       |
| ---- | ------------------------------- | --------------------------------- |
| **需求** | 明确目标、范围、验收标准；识别隐含约束与依赖            | 在目标或验收标准模糊时直接开工                   |
| **规划** | 探查现状；评估影响面与风险；拆解为可验证的小步骤          | 凭猜测定位代码、跳过探查直接写                  |
| **编码** | 遵循本项目编码规范；小步提交；保证既有功能不回归          | 静默扩大改动范围；破坏性替换或删除未要求的内容          |
| **验证** | 运行最小验证（测试 / 构建 / 渲染 / 重算）；主动寻找反证  | 以 "文件存在、语法通过" 冒充 "功能正确"          |
| **交付** | 说明产物名、路径、打开方式、验证结果与已知缺口           | 隐藏未完成项、悄悄降级交付物                    |

### 3.1 需求阶段附加约束



* 单任务单目标：一次只做一件事，复合需求必须拆分。

* 验收标准必须是**可检查的**（"页面能打开并显示 3 条数据"），而不是可争议的（"体验更好"）。

* 存在关键歧义且会影响结果时，列出选项一次性问清；不影响结果的歧义自行选择并注明。

### 3.2 规划阶段附加约束



* 连续两次探查不再改变计划即停止探查、开始执行，不得以搜索代替行动。

* 需要偏离用户点名的技术栈、结构、格式时，先说明理由并取得同意，不得静默替换。

### 3.3 文档先行约束



* **先确认文档再编码**：编码开始前必须先完成相关设计文档（实现方案、模块设计等）并取得确认，文档确认通过后方可进入编码。

## 4. 代码约束



1. 遵循各项目编码规范（语言规范、命名、结构），本规范为顶层约束，不替代具体语言规范。

2. 不引入安全漏洞：注入（SQL / 命令 / XSS）、越权、敏感信息硬编码等一律禁止。

3. 优先编辑现有文件而非新建；新建文件需有明确必要。

4. 注释说明 "为什么" 而非复述 "是什么"；对外接口保持清晰可读。

5. 遇到意外文件或状态，先调查再处置，不得直接覆盖或删除 —— 可能是进行中的工作。

## 5. 验证与质量门



交付 / 合并前必须逐项通过以下质量门：

* [ ] 需求中的每一项都有对应实现，无遗漏、无多余；

* [ ] 验证动作已实际运行且通过（运行真实命令 / 测试 / 打开渲染结果，而非仅检查文件存在）；

* [ ] 未改动点名范围之外的内容；

* [ ] 无安全红线问题；

* [ ] 数据与数字有来源，或已标注 "估算 / 待补充" 及口径；

* [ ] 页数、字数、条目数等实数与需求口径一致；

* [ ] 项目文档与测试用例齐备，且与代码实现一致。

## 6. 红线禁令（MUST NOT）



1. 不得破坏、删除、重命名未要求处理的现有功能或文件。

2. 不得引入 OWASP Top 10 类安全漏洞，不得绕过安全与权限校验。

3. 不得编造验证结果、数据来源或引用。

4. 不得静默降级交付物（如把应自动完成的工作改成教程、模板或让用户手工操作）。

5. 不得在未经授权时向额外账号、仓库、云盘或群组写入内容。

6. 不得未经确认执行不可逆的高风险操作。

## 7. 技术栈与环境约束



1. **高性能优先 C/C++**：在需要高性能的场景下（计算密集、实时性要求高、资源受限等），技术栈优先使用 C/C++；确需改用其他语言时，说明理由并经确认。

2. **Python 环境隔离**：每个项目的 Python 执行必须使用独立的虚拟环境（venv / conda / virtualenv 等），依赖在项目内声明（requirements.txt / pyproject.toml 等），禁止直接使用全局解释器与全局包。

## 8. 项目文档与测试基线



1. **项目文档**：项目必须具备完善的文档，包括但不限于：项目整体规划文档、项目类图 / 流程图、各模块设计文档、重要知识点 / 算法说明文档等。

2. **测试用例**：项目必须具备完善的测试用例，覆盖接口测试、单元测试、整体功能测试等。

3. **同步修订**：修复代码的同时，必须同步修复对应的文档内容与测试用例，保持代码、文档、测试三者一致。

## 9. 工作方式



工作方式在任务开始前由需求方明确指定；未指定时默认进入**单步模式**。

1. **单步模式**：每一步修改（探查、读取除外）都要先给出方案与影响说明，得到确认后再执行；每步完成即汇报结果，等待下一步确认。

2. **全自动模式**：所有执行均按推荐操作进行，中途不中断、不逐项请示；持续执行直到完成全部验收项，最后统一汇报结果与验证情况。

## 10. 会话交接



1. **会话交接文档**：每次 AI 会话结束时，必须更新会话交接文档（按 `templates/会话交接文档模板.md`），记录：任务状态、已完成 / 未完成事项、关键决策与依据、产物路径、待确认事项、下一步建议。

2. 交接文档供下一轮对话快速承接，避免重复探查与上下文丢失；任务未完成时，交接文档必须能支撑下一位执行者直接续接。

3. 交接文档描述必须与项目实际状态一致（对齐「项目文档与测试基线」的同步要求）。

## 11. 规范演进



* 本规范由基准项目统一维护，下游项目可在此基础上制定**更严**的约束，不得放宽。

* 修改需经评审并升级版本号，变更记录写入下方版本表。

* 新规范（Git 与 CI/CD 规范、编码规范、任务模板、验收标准等）以本规范为总纲挂接发布。
