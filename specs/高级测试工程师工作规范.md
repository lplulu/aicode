## 1. 角色定位

高级测试工程师是 VibeCoding 工作流中的**质量把关者**：重心为**质量风险把控、测试方案设计、专项测试落地、质量推动与体系优化**，不局限于用例执行。

本规范承接 VCS-WF-001 总纲第 8 节「项目文档与测试基线」中的**测试基线**：项目测试相关的策略、设计、执行与质量评估，统一由本角色承担。

## 2. 职责边界

* **负责**：需求可测性评审与风险识别、测试策略与方案、用例设计与评审、专项测试（接口自动化 / 性能 / 稳定性 / 安全 / 兼容性）、缺陷管理与根因分析、版本质量评估与上线风险判定、测试资产与工具建设、线上问题复盘。

* **不负责**：业务代码的编码实现（VCS-ENG-001 工程师职责）、对交付物的独立评审结论（VCS-REV-001 评审员职责）。

* **与工程师的分工**：工程师必须完成**自测**（VCS-ENG-001 第 10 节），但**自测不能替代独立测试**；未经本角色确认的测试结论，不得作为交付依据。

* **与评审员的分工**：评审员核查「测试是否存在、是否可运行、是否与代码一致」；本角色对「测得够不够、风险是否可接受」负责 —— 两者互不替代、互不越位。

* 当测试范围、准入准出标准或上线结论需要调整时，先上报确认，不得单方面放宽。

## 3. 工作原则

1. **质量前置**：测试在需求阶段介入，不等到提测才开始。

2. **风险优先**：资源有限时优先覆盖高风险链路与核心场景。

3. **客观量化**：结论基于可复现的数据与证据，不以「感觉没问题」下判断。

4. **持续改进**：每次漏测与线上故障都必须转化为用例、自动化或监控的补充。

5. **坦诚沟通**：基于事实与数据沟通质量风险，聚焦质量改进而非责任归属；风险不隐瞒、不淡化，重大风险必须及时升级（对齐 VCS-REV-001「事实有源」与总纲「不得编造验证结果」）。

## 4. 作业流程（测试六步）

```
需求评审 → 测试策略 → 测试设计 → 测试执行 → 质量评估 → 上线复盘
```

1. **需求评审**：识别业务、逻辑、可测性风险，输出风险清单。

2. **测试策略**：制定项目 / 模块测试方案，定义范围、测试类型、准入准出标准。

3. **测试设计**：主导用例设计评审，覆盖主流程、边界、异常场景，指导初级测试。

4. **测试执行**：按准入门槛收测，按风险优先级执行，缺陷闭环与关联回归。

5. **质量评估**：输出版本质量报告，评估上线风险，重大问题及时升级。

6. **上线复盘**：灰度巡检、线上问题跟进、项目质量复盘与改进项落地。

## 5. 各阶段规范

### 5.1 需求阶段

提前研读需求与原型；评审中识别逻辑漏洞、外部依赖与可测性问题；评估测试工作量与风险。**需求不清不启动测试设计**（对齐总纲「验收先行」原则）。

### 5.2 测试设计阶段

编写测试方案与用例；组织用例评审（需求方、工程师、评审员参与）；提前准备测试环境、测试数据、Mock 与自动化脚本。用例须覆盖：主流程、边界值、异常与失败路径、权限与并发场景。

### 5.3 测试执行阶段

严格执行**提测准入标准**，不达标则退回；按风险优先级执行，优先高风险链路；缺陷信息必须完整（版本、环境、复现步骤、日志 / 截图、期望与实际结果）；缺陷修复后做**关联回归**而非仅验证单点；阻塞问题及时同步。

### 5.4 上线与收尾阶段

核对上线清单与回滚方案；输出版本测试总结；上线后执行灰度巡检；组织项目质量复盘，跟进改进项落地。

## 6. 缺陷管理

1. **缺陷分级**：P0 阻断、P1 严重、P2 一般、P3 轻微；**P0 / P1 上线前必须闭环**。

2. 精准定位缺陷根因，跟踪至闭环；对高频缺陷做根因分析并推动源头修复。

3. **不得未经评审擅自降级 P0 / P1 缺陷**（见第 10 节红线）。

> **分级口径说明（重要）**：本节的 P0–P3 属于**测试域的缺陷分级**；VCS-REV-001 第 7 节的 P0 / P1 / P2 属于**评审域的意见分级**。二者同名而不同义，任何文档、报告与沟通中必须标明所属域（如「缺陷 P1」「评审意见 P1」），禁止混用。

## 7. 专项测试规范

* **接口测试**：覆盖正常、异常参数与权限校验；在 CI 中自动执行；校验数据一致性与错误码语义。

* **性能测试**：提前定义指标（TPS / 响应时间 / 资源占用）；**禁止压生产**；压测后定位瓶颈并输出优化建议。

* **稳定性测试**：覆盖长时间运行、异常重启、依赖抖动下的恢复能力。

* **安全测试**：覆盖越权、注入、敏感信息泄露等红线项（对齐总纲「不引入安全漏洞」）。

* **兼容性测试**：覆盖主流终端、操作系统与浏览器。

## 8. 交付物清单

需求风险记录、测试方案、测试用例、专项测试报告、版本测试总结、复盘文档。

| 交付物 | 模板 |
|---|---|
| 测试方案（策略 / 范围 / 准入准出） | 无独立模板，纳入设计文档「测试策略要点」（`templates/设计文档模板.md` 第 8 节） |
| 测试用例 | `templates/测试用例模板.md` |
| 专项测试报告 / 版本测试总结 / 复盘文档 | `templates/测试报告模板.md` |

## 9. 线上问题处理

1. 快速确认影响范围与严重程度，先止血后定位。

2. 区分成因：缺陷 / 配置 / 外部依赖 / 数据问题，避免误判归因。

3. 提交高优缺陷并跟踪闭环。

4. **复盘漏测原因**，补充用例、自动化或监控 —— 未转化为资产的复盘视为未完成。

## 10. 红线（测试工程师 MUST NOT）

1. 不得隐瞒重大质量风险、不得强行放行上线。

2. 不得伪造测试记录、测试数据或测试报告（含由 AI 生成后未经实际执行的「假执行」结论）。

3. 不得在生产环境随意执行测试、构造数据或执行压测。

4. 不得泄露敏感业务数据与生产数据。

5. 不得未经评审擅自降级 P0 / P1 缺陷。

6. 不得编造验证结果、数据来源或引用（对齐总纲第 6 节红线）。

## 11. AI 协作附加约束（VibeCoding 场景）

1. AI 可辅助生成用例与脚本，但**必须经过人工评审与实际执行**；未经执行的生成内容不得计入测试覆盖率。

2. 测试资产与代码同样受「同一文件不可并行编辑」约束（总纲第 4 节第 6 条）：同一用例 / 脚本文件同一时刻只允许单一写入者。

3. 术语统一采用项目 `GLOSSARY.md`；新增测试领域概念须同步写入术语表（总纲第 8 节第 4 款）。

4. 测试结论中的每一条数据（通过率、缺陷数、性能指标）必须有来源或写明口径，禁止估算而不标注。

## 12. 考核与度量要点（参考）

| 维度 | 度量项 |
|---|---|
| 质量结果 | 线上漏测率；P0 / P1 缺陷的上线情况（上线前闭环率） |
| 风险识别 | 需求阶段风险识别的及时性与覆盖情况 |
| 资产质量 | 测试方案与用例的评审质量、场景覆盖充分性 |
| 效能建设 | 自动化覆盖率、测试工具 / 平台落地情况 |
| 体系贡献 | 流程改进项落地、知识沉淀与复用情况 |

度量数据须有来源或写明口径（对齐「事实有源」原则）；**不得以度量指标倒逼放宽准出标准** —— 指标用于改进，不用于放行。
